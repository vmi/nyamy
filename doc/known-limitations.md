# 既知の制約と、見送った案

原因を特定したうえで「対処しない」と決着した制約と、検討して採らなかった設計案をまとめる。**同じ検討を繰り返さないための記録**であり、再提案するときは各項の「再提案するときに問うこと」を先に確かめること。

---

## 1. 昇格ウィンドウは操作できない

タスク マネージャーやレジストリ エディタのように昇格して動作するアプリケーションがフォアグラウンドにある間、非昇格の NYamy は UIPI により次のことができない。

- **ウィンドウ調査**。`MayuMessage_notifyName` を送っても届かず、結果がログに出ない
- **ハイライト枠の表示**。対象が「常に手前に表示」だと枠が完全に隠れる
- **`SendInput()` による注入**。丸ごと破棄される ([input-injection.md](input-injection.md))

NYamy 自身を昇格させれば解決するが常用は勧めない、という結論。マニュアル (`03-menu.md` / `01-install.md`) に制約として記載済み。

---

## 2. フック DLL の遅延アンロードによる二重入力

`nyamy64.dll` は `WH_GETMESSAGE` / `WH_CALLWNDPROC` のグローバルフックとして全 64bit GUI プロセスに注入される。`UnhookWindowsHookEx()` のあとも、各注入先プロセスは**次にメッセージを処理するまで DLL をアンロードしない**。

これが 2 つの形で表面化する。

- **ビルド時**: アイドルなプロセスが何時間も DLL を掴んだままになり、リビルドで `LNK1104` (nyamy64.dll を開けない) → `nyamy64.lib` 未生成 → `nyamy.exe` のリンク失敗
- **実行時**: NYamy を短時間に何度も終了→起動したあと、その間ずっと起動しっぱなしだったプロセスで**キー入力が 2 回入力になる**。古い DLL が残ったまま新しいフックが乗り、両方がキーを処理するため

`uninstallMessageHook()` にアンフック後の `SendNotifyMessage(HWND_BROADCAST, WM_NULL, 0, 0)` を入れて全 GUI スレッドを起こし、即時アンロードを促してある (2026-08-04)。ただしアンロードのタイミングは注入先プロセスのメッセージポンプ任せで、NYamy から強制できない (対象スレッドが応答なし・サスペンド中、対象が昇格プロセスでブロードキャストが届かない、など)。

**発生確率を下げることはできても根絶を保証する手段がない**ため、これ以上の技術的対処は行わない。**再現したら対象プロセスを再起動する**のが対処法。

---

## 3. 多重起動まわりの既知の不整合

2026-08-08 に `wWinMain()` の多重起動チェックが機能していなかったのを修正した (`5fc8820`)。`CreateMutex()` は既存のミューテックスに対しても有効なハンドルを返すため、`mutex == nullptr` では検出できていなかった。

修正後も残っている不整合が 2 つある。いずれも実害が小さいので手を付けていない。

- `MUTEX_MAYU_EXCLUSIVE_RUNNING` (`mayu.h`) は固定 GUID で、**VERSION サフィックスもビルド種別も付かない**。そのため Release / Debug / 異なるバージョンが相互に排他される。`Global\` プレフィクスが無いのでセッション毎
- `NOTIFY_MAILSLOT_NAME` だけ `addSessionId()` を通しておらず、**マシン全体**の名前になっている

なお「NYamy を 2 つ起動し、片方を一時的に無効化して入れ替える」というデバッグ手順は、上記の排他チェック修正によって使えなくなっている。アクティブ/パッシブの所有権モデルは未着手。

## 4. 見送った案

### 4.1 スレッド削減のためのリアクタ

`WaitForMultipleObjects` + 同期オブジェクト/ハンドラの登録機構でスレッドを減らす案を検討し、**見送った** (2026-08-08)。

1. **待機可能ハンドルが元々ゼロ。** `nyamy.exe` の 7 スレッドのうち待っているものは `GetMessage` × 3 (UI + InputHandler 2 本)、同期パイプ × 2、メールスロット × 1 で、`WaitForMultipleObjects` に載るものが 1 つも無い。主作業はリアクタではなく各トランスポートの待機可能化になり、順序が逆
2. **ハンドラが短時間で返らない。** engine は `&Sync` / `&Wait` で最大 5 秒駐機し、`ShellExecute()` も呼ぶ。通知の受信を UI スレッドの APC から剥がしたのは、まさにこの共有が原因で `&Sync` が必ずタイムアウトしたため。汎用リアクタは同じ性質を別名で再導入することになる
3. **スレッド 1 本のコストは予約 1MB + 数 KB で、スレッド数は定数**。キー数にもウィンドウ数にもスケールしないので削減の実利がほぼ無い

低レベルフック (`WH_KEYBOARD_LL` / `WH_MOUSE_LL`) はインストールしたスレッドのメッセージポンプでしか配送されないため、そもそもリアクタに載せられない。

派生案の **InputHandler 2 本を 1 本に統合する** (1 スレッドで両フックを install。7→6 本) も、同じ理由 3 により **2026-08-17 に見送りを決定**した。

### 4.2 フック通知の共有メモリリング

フック通知をメールスロットから共有メモリ上の有界 MPMC リングへ移す作業を実装まで進めたうえで、**2026-08-10 に破棄**した。全コミットはブランチ `backup/notify-ring-20260810` に残してある。

破棄の理由は、選定時に**破壊耐性という軸を評価していなかった**こと。

- **メールスロットはキューの状態がカーネルにあり、ユーザーモードから壊せない。** リングはインデックス (`enqueuePos` / `dequeuePos` / `seq`) まで共有メモリ上にある
- 264KB が**全 GUI プロセスに書き込み可能でマップされる**。悪意よりも、どれか 1 つのプロセスの暴走ポインタの着弾のほうが現実的
- メッセージ内容の破壊は防御済みだったが、**インデックスの破壊は無防備**で、`dequeuePos` が `enqueuePos` を追い越すケースは自己回復しない
- 共有メモリ上にレイアウトを持つため、**VERSION 据え置きでレイアウトだけ変えると壊れる** (開発中のバイナリ差し替えで起きる)

決定打は、**当初の目的だった再起動対応がメールスロットのままでも約 100 行で実現できた**こと。リングが明確に勝っていたのはドロップ計数だけだが、それは 64 スロット固定という自ら作った制約への対処であり、カーネルキューが伸びるメールスロットでは数えるべきドロップがほとんど発生しない。

**再提案するときに問うこと**: 「ブロックしない」はメールスロットも満たしている。リングの利点として残るのは**ドロップ計数とカーネル遷移の回避だけ**であり、その 2 つが破壊耐性・レイアウト結合・露出面積・約 600 行のコードに見合うか。なお破棄時点で未修正のバグが残っている (`create()` の失敗が無視され、受信スレッドが CPU 1 コアを 100% 使う無限ループに入る、など) ので、ブランチを復活させるならそこから。

### 4.3 インストーラの置き換え

`s/install.ps1` / `s/uninstall.ps1` を WiX / Inno Setup / NSIS / MSIX / Velopack へ置き換える案を評価し、**見送った** (2026-08-11)。

難所はファイルコピーではなく「**グローバルフック DLL が他プロセスにマップされたままの状態での置換**」で、インストーラの標準機構がどれも使えない。

- `MOVEFILE_DELAY_UNTIL_REBOOT` (MSI の再起動スケジュール、Inno の `restartreplace`) は**管理者権限必須**。インストール先が `%LOCALAPPDATA%\Programs\NYamy` の非昇格インストールなので使えない
- MSI の Restart Manager による FilesInUse ダイアログは「掴んでいるプロセスを閉じろ」と出すが、`nyamy64.dll` を掴んでいるのは explorer.exe を含む 20 以上のプロセス (2 節)。UX として破綻する
- つまりリネーム退避はどのインストーラを選んでも自前実装が必要で、宣言的な WiX ではカスタムアクション DLL 送りになり最も高くつく
- 副次的に、perUser MSI / Inno / NSIS はいずれも ARP 情報を `HKCU\...\Uninstall` に書くため、「レジストリへの書き込みを行わない」という方針が崩れる

**再提案するときに問うこと**: 「MSI 形式を要求する配布先 (企業の Intune など) が実在するか」「コード署名証明書を取るか」。両方 No なら結論は変わらない。Yes なら WiX、署名するが MSI 不要なら Inno Setup が次点。MSIX は `%ProgramFiles%\WindowsApps` の ACL 下でフック DLL が全プロセスから読めるかが不明なので、PoC なしに選んではいけない。

配布チャネルとしての winget マニフェスト (現在の zip を portable 型で登録) は、この判断とは独立にいつでも追加できる。
