# DPI aware 対応

NYamy を Per-Monitor v2 の DPI aware プロセスにするにあたって必要な作業と、その際に
踏まえておくべき Windows の挙動をまとめる。記載の挙動は 1920x1080@100%（主）と
1920x1200@125%（副）の 2 画面構成での実測に基づく。

---

## 1. awareness の宣言

### マニフェスト

`nyamy.manifest` を埋め込み、`nyamy.vcxproj` の各構成から
`<AdditionalManifestFiles>` で参照する。

```xml
<assembly manifestVersion="1.0" xmlns="urn:schemas-microsoft-com:asm.v1">
  <assemblyIdentity type="win32" name="nyamy" version="1.0.0.0"/>
  <application xmlns="urn:schemas-microsoft-com:asm.v3">
    <windowsSettings>
      <dpiAware xmlns="http://schemas.microsoft.com/SMI/2005/WindowsSettings">true/pm</dpiAware>
      <dpiAwareness xmlns="http://schemas.microsoft.com/SMI/2016/WindowsSettings">PerMonitorV2, PerMonitor, system</dpiAwareness>
    </windowsSettings>
  </application>
</assembly>
```

**`<application>` には `urn:schemas-microsoft-com:asm.v3` を明示する。** 囲みの
`<assembly>` は asm.v1 であり、名前空間を書かないと `<application>` がそれを継承した
まま埋め込まれる。`windowsSettings` が定義されているのは asm.v3 なので、この形でないと
無視されうる。

実行時 API (`SetProcessDpiAwarenessContext`) ではなくマニフェストを使う。awareness は
最初のウィンドウ作成やフック設置より前に確定している必要があり、マニフェストなら
順序を考えなくて済む。

### 埋め込まれたか確認する

MSBuild は自身が生成する `trustInfo` とマージするため、意図した形で入ったかは
ビルド後の実行ファイルから確認する。PowerShell で `RT_MANIFEST`（リソース型 24、
名前 1）を取り出し、`<application xmlns="urn:schemas-microsoft-com:asm.v3">` の下に
両要素があることを見る。

### 実行時の確認

バージョンダイアログに次を表示している。`awareness=per-monitor-v2` でなければ
マニフェストが効いていない。

```
GetAwarenessFromDpiAwarenessContext(GetThreadDpiAwarenessContext())
```

PMv2 と PMv1 は `DPI_AWARENESS` の値が同じなので、区別するには
`AreDpiAwarenessContextsEqual(ctx, DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2)` が要る。

## 2. 座標系の実際

aware 化の本質は「USER32 の座標が 96dpi 空間への仮想化をやめて物理ピクセルになる」
ことにある。API ごとに挙動が異なるので、以下を前提にする。

| API | unaware のとき | aware (PMv2) のとき |
|---|---|---|
| `GetWindowRect` / `GetCursorPos` / `GetSystemMetrics` | 仮想化される | 物理ピクセル |
| `MSLLHOOKSTRUCT::pt`（低レベルマウスフック） | **仮想化されない（常に物理）** | 物理ピクセル |
| `GetDpiForWindow(hwnd)` | 対象ウィンドウの実 DPI を返す | 同左 |
| `GetDpiForMonitor(MDT_EFFECTIVE_DPI)` | 呼び出し側に合わせて 96 | モニタの実 DPI |
| `DwmGetWindowAttribute` の座標系アトリビュート | 物理ピクセル | 物理ピクセル |

実測例（副モニタ 125% 上のウィンドウ）:

```
unaware : monitorRect=(1920,0)-(3456,960)   ウィンドウ 569x405
aware   : monitorRect=(1920,0)-(3840,1200)  ウィンドウ 711x506   (= 569x405 の 1.25 倍)
```

### 低レベルマウスフックとの不整合は aware 化で解消する

`MSLLHOOKSTRUCT::pt` は awareness に関わらず物理ピクセルで届く。一方 `GetCursorPos()`
は unaware のとき仮想化される。**つまり unaware のプロセスでこの 2 つを引き算すると
副モニタ上で座標空間が混ざる。**

```
副モニタ上での実測（unaware）: pt=(2386,494)  GetCursorPos=(2293,395)   食い違う
aware 化後                    : pt=(2475,496)  GetCursorPos=(2475,496)   一致
```

`&MouseHook(WindowMove)` のドラッグ量、ホイール量、絶対座標の注入がこれに依存して
いる。aware 化はこの不整合を解消する側であって、新たに壊す側ではない。

### 倍率にはモニタの DPI を使う

設定値などを実 DPI へ換算するとき、**対象ウィンドウの DPI ではなくモニタの DPI を
使う**。`GetDpiForWindow()` は「そのウィンドウが何 DPI で描かれているか」を返すため、
**対象プロセスが DPI unaware だと 125% のモニタ上でも 96 を返す**。こちらが
`SetWindowPos` へ渡す座標はデスクトップの空間なので、倍率を決めるのはモニタ側。

`windowstool` に用意してある入口:

- `dpiForPoint(POINT)` — 点が乗っているモニタの DPI
- `dpiForWindowMonitor(HWND)` — ウィンドウが乗っているモニタの DPI
- `scaleFromLogical(px, dpi)` — 96dpi 前提の長さを実 DPI へ換算

`GetDpiForMonitor` は shcore.dll から静的にリンクしている。実行時解決は何も守らない
——このバイナリは既に USER32 から `GetDpiForWindow` などを静的にインポートしており、
マニフェストが Per-Monitor v2 を要求している以上、Windows 10 1703 未満ではそもそも
ロードできないため。取得に失敗した場合は 96 を返し、**失敗したら何も拡大しない**側へ倒す。

なお `MDT_RAW_DPI` は環境により取得に失敗する（実測で副モニタに対し失敗）。判断に
使わないこと。

## 3. 固定ピクセルの置き換え

96dpi 前提で直値になっている寸法を洗い出し、`scaleFromLogical()` か
`GetSystemMetricsForDpi()` を通す。`scaleFromLogical()` は 96dpi では恒等で、
非ゼロの入力が 0 に潰れないことを保証する（1px のナッジが no-op にならない）。

置き換えたもの:

| 箇所 | 内容 |
|---|---|
| `layoutmanager.cpp` | サイズグリップの `SM_CXHTHUMB` / `SM_CYVTHUMB` |
| `windowstool.cpp` | アイコン読み込みの 16x16 / 32x32 → `SM_CXSMICON` / `SM_CXICON` |
| `target.cpp` | クロスヘアの `SM_CXICON`。カーソルリソースは 32x32 固定なので `DrawIcon` を `DrawIconEx` に変えて伸長する |
| `focus.cpp` | キャレット幅の直値 2px |

### 描画とヒットテストで同じ値を共有する

サイズグリップのように「描く」と「掴む」で同じ寸法を使う箇所は、計算を 1 箇所に
まとめる（`LayoutManager::sizeGripRect()`）。片方だけ DPI 対応すると、**見えているのに
掴めないグリップ**という気付きにくい不具合になる。

### タスクトレイアイコンはシステム DPI

描画するのは通知領域であって自分のウィンドウではないため、`GetDpiForSystem()` を
使う。自分の隠しウィンドウの DPI を使っても意味がない。

## 4. 設定と永続データの単位

### 設定ファイルのピクセル値

`.mayu.rb` に書かれたピクセル値は **96dpi 基準の論理ピクセル**と定義し、使用直前に
対象モニタの DPI で換算する。既存の設定が同じ見た目の距離で動き続けること、および
100% のモニタ上では恒等変換になり回帰の切り分けが容易であることが理由。

対象は `&MouseMove` / `&WindowMove(To)` / `&WindowResizeTo` / `drag-threshold`。
矩形（ウィンドウ位置や作業領域）は既にデスクトップの空間にあるため触らない。
換算するのは設定由来の値だけ。

`&WindowResizeTo` は正値（絶対サイズ）も負値（デスクトップより N px 小さく）も
どちらも設定由来なので、両方換算する。

### ini に保存する値

**保存形式を 96dpi の正準値に固定し、使用直前に換算する。** 実 DPI の値をそのまま
保存すると、保存時と復元時で DPI が違ったときに意味が変わる。

- `logFont`: `LOGFONT::lfHeight` は 96dpi の値として保持し、`CreateFontIndirect` の
  直前で換算する。`ChooseFont` へは換算した複製を渡し、戻り値を 96dpi へ戻して保存
  する。この方式なら aware 化前に保存された値がそのまま正しく、移行処理が要らない。
- `logWindowPlacement`: `WINDOWPLACEMENT` は座標そのものなので換算では吸収できない。
  **キー名を変えて（`logWindowPlacementPhysical`）新旧を別物として扱う。**
  移行は次の 2 点で完結する。
  - 新キーが無ければ**旧キーを読む**。2 つの空間が食い違うのは、システムの拡大率と
    異なるモニタ上に置かれたウィンドウだけであり、そこで出た誤差は画面内へ引き戻す
    処理が吸収する。位置を引き継げる利点の方が大きい。
  - 保存時に**旧キーを削除する**。以後フォールバックは効かなくなるので、古い値が
    残り続けて後から読まれることがない。

### ラスタフォント前提の LOGFONT

ビットマップフォント（`Terminal` など）は DPI が変わって要求サイズが変わると、その
字面を持たないため GDI が引き伸ばして表示が粗くなる。unaware の頃は窓ごと DWM が
拡大していたので粗さが均一でめだたなかったが、aware 化で表面化する。

スケーラブルなフォントを既定にし、あわせて次の 3 つを既定値へ戻す。これらは
ラスタフォント向けの指定である。

| フィールド | ラスタ前提の値 | 既定値 |
|---|---|---|
| `lfOutPrecision` | 1 (`OUT_STRING_PRECIS`) | 0 (`OUT_DEFAULT_PRECIS`) |
| `lfClipPrecision` | 2 (`CLIP_STROKE_PRECIS`) | 0 (`CLIP_DEFAULT_PRECIS`) |
| `lfQuality` | 1 (`DRAFT_QUALITY`) | 0 (`DEFAULT_QUALITY`) |

`lfCharSet` はフォントに合わせる（`MS Gothic` なら `SHIFTJIS_CHARSET`、
`Lucida Console` なら `ANSI_CHARSET`）。フォントが存在しない環境では、この指定を
手掛かりに代替フォントが選ばれる。

## 5. ダイアログの DPI 変更対応

**ここが最も間違えやすい。** 自前のレイアウト機構（`LayoutManager`）を持つ場合、
ダイアログマネージャとの役割分担を正確に把握する必要がある。

### ダイアログマネージャが何をするか

Per-Monitor v2 は**ウィンドウ・コントロール・そのフォントを自分で拡大する**。
しかも **`WM_DPICHANGED` が届く前に済ませている**。

```
WM_GETDPISCALEDSIZE   ← まだ何も拡大されていない
  （ウィンドウのリサイズ、コントロールとフォントの拡大）
  WM_SIZE             ← ここで自前のレイアウトが走ると拡大を打ち消す
WM_DPICHANGED         ← 届いた時点で上記は完了している
```

実測（96→120、「閉じる」ボタン）:

```
96dpi 時          : 88x23
WM_DPICHANGED 到達時: 100x28   ← ダイアログマネージャが拡大済み
```

### 守るべき 4 点

**(1) DPI 変更中は自前のレイアウト調整を止める。**
`WM_GETDPISCALEDSIZE` でフラグを立て、`WM_DPICHANGED` の処理が終わるまで `WM_SIZE`
経由の再配置を抑止する。これをしないと、旧 DPI の基準でコントロールの大きさと位置を
上書きし、ダイアログマネージャの拡大を打ち消してしまう。**「PMv2 はダイアログを
拡大しない」ように見えたら、まずこれを疑う。**

**(2) フォントは自前で拡大しない。**
ダイアログマネージャが済ませているため、重ねて掛けると倍率が二重になる。コントロールの
大きさは自前のレイアウトが矩形から決め直すので正しく見えてしまい、**フォントだけが
おかしくなる**という分かりにくい壊れ方をする。

自前で `WM_SETFONT` したフォント（ログの編集コントロールなど）だけは例外で、これは
ダイアログマネージャの管理外なので入れ直す。その際は 96dpi の正準値から換算する。
ダイアログマネージャはウィンドウの変化した比で拡大するため、そちらに任せるとモニタを
往復するうちに誤差が溜まる。

**(3) レイアウトの基準は比で換算する。実測で読み直さない。**
`LayoutManager::Item` の `m_rcParent` は「今の親の大きさ」ではなく、**`m_rc` を記録
した時点の親の大きさ**であり、`adjust()` は両者の差を端からのオフセットとして使う。
実測で読み直すと差が消え、コントロールはダイアログテンプレート上の位置に落ちる
（テンプレートがボタン列の高さしかないダイアログでは、上端の帯に全部が集まる）。

`m_rc` と `m_rcParent` の**両方**を DPI 比で換算する。オフセットが正しく拡大されれば
足り、ウィンドウ自体が旧サイズのちょうど比倍になる必要はない。

**(4) 基準の変換は同期的に行う。**
「拡大が終わってから投げたメッセージで処理する」方式は破綻する。配置の復元
（`SetWindowPlacement`）は `WM_INITDIALOG` の中で DPI と大きさを一度に変えるため、
その後の `adjust()` が旧 DPI の基準で走ってしまう。この `adjust()` は `WM_SIZE` を
経由しないので (1) の抑止も効かない。

### ウィンドウの大きさはシステムの計算に従う

ウィンドウの新しい大きさは **DPI 比にならない**（実測で 1.25 倍の変化に対し幅は
1.14 倍）。Windows がダイアログテンプレートから再計算するためで、テンプレートより
大きく広げられたダイアログでは比例しない。

これを `WM_GETDPISCALEDSIZE` で「現在の大きさ × DPI 比」に上書きしてはいけない。
**フォントの倍率はダイアログマネージャが決めており、こちらから変えられない**ため、
ウィンドウだけ別の倍率にすると必ずフォントとジオメトリが食い違う。表示領域の幅が
数ピクセル合わないのはその代償であり、一貫性と引き換えにする価値はない。

### 変更前の状態を控える

スクロール位置のように「変更をまたいで保ちたいもの」は、**`WM_GETDPISCALEDSIZE` の
時点**で控える。`WM_DPICHANGED` ではもう遅い。その間にフォントの拡大とウィンドウの
リサイズで折り返しが二度変わり、表示位置も動いている。

編集コントロールの表示位置は**文字位置**でアンカーする。スクロール系のメッセージが
数えるのは論理行ではなく**折り返し後の表示行**で、フォントの高さが変わると折り返し
位置そのものが変わるため、行番号は変更の前後で別の場所を指す。文字位置なら折り返しが
何度変わっても同じ場所を指す。

なおログのように末尾へ追従する表示では、変更前に末尾が見えていたかを判定し、その
場合は末尾へスクロールし直す。先頭を固定すると最新行が画面外に出る。

## 6. 低レベルフック内の制約

低レベルフックのコールバックは `LowLevelHooksTimeout` を超えるとその入力に対して
**読み飛ばされる**。ボタンの解放が届かなければ押しっぱなしとして残る。

- **ログ出力を置かない。** ログのロックは UI スレッドも取るため、ログの流量が多い
  起動直後などに待たされる。
- **DPI の取得はボタン押下時に一度だけ行う。** `drag-threshold` の換算値は押下時に
  解決して保持する。押している間はモニタが変わらないので十分。
- **フックの中で初めて DLL を読み込ませない。** `GetDpiForMonitor` を提供する
  shcore.dll は静的リンクなので、ローダが起動時に解決する。実行時解決に戻すなら、
  初回の `LoadLibrary` がフックの中で起きないよう別途手当てすること。

## 7. プロセス境界

**フック DLL が測った座標を nyamy.exe 側へ渡してはいけない。** DLL は注入先プロセスの
awareness を継承するため、座標空間が一致する保証がない。ウィンドウの幾何情報が必要な
ときは、HWND だけを渡して nyamy.exe 側で測り直す。

`g_hookData` は共有メモリなので、ここに座標のフィールドを増やすときは特に注意する。
現在の唯一の座標 `m_mousePos` は nyamy.exe 内でのみ読み書きされており、この性質が
崩れると混在 DPI 環境で破綻する。

## 8. 検証

### 構成

混在 DPI が必須。**主モニタを 100% にしておくと、システム DPI が 96 のままになり
「主モニタ上で挙動が変わったらそれは換算以外の不具合」という判定基準が使える。**

### 3 種類に分けて通す

1. **静的** — スケールを設定してから起動。固定メトリクス・アイコン・フォント・
   ini の移行。
2. **動的** — 起動後にスケールを変更（単一モニタでも `WM_DPICHANGED` は飛ぶ）。
   モニタ間ドラッグより再現が確実なので先に通す。
3. **混在 DPI** — モニタ間の移動、境界にまたがった状態、別 DPI モニタでの保存と復元。

### 見落としやすいケース

- **副モニタ側に保存された配置で起動する。** `WM_INITDIALOG` の中で DPI と大きさが
  同時に変わる唯一の経路で、他が全て正常でもここだけ破綻することがある。
- **モニタを取り外した状態での復元。**
- **低 DPI モニタ側で最小サイズ制限に引っかかって縮められなくならないか。**
- **折り返しを有効にして長い行の途中を先頭にした状態**での DPI 変更。

### 主副を入れ替えた構成

主モニタが 100% の間は「物理」と「システム DPI 空間」が偶然一致している。
座標系についての結論を一般化する前に、**システム DPI が 96 でない構成**でも
確かめること。

## 9. 既知の限界

- **DPI 境界をまたぐ「位置＋サイズ」指定の `SetWindowPos` はサイズが二重に
  スケールされる。** 移動先の DPI に合わせて OS が対象アプリへ `WM_DPICHANGED` を
  送るため、指定したサイズの上にもう一度倍率が乗る。実測では指定 `569x405` に対し
  結果が `455x324`（正確に 1/1.25）。位置は指定どおりになる。
  - 自分のウィンドウであれば、**移動先のモニタに乗った状態でサイズを入れ直す**
    ことで回避できる（DPI 境界を二度越えないため再スケールされない）。
    ログウィンドウの配置復元はこの方法で対処している。
  - 他プロセスのウィンドウを操作する `&WindowHMaximize` の復元などは未対処。
- **ダイアログのフォントの倍率はダイアログマネージャが決める。** DPI 比ではなく
  ウィンドウの実際の変化比になるため、表示領域の寸法が数ピクセル理想と合わない。
- `MDT_RAW_DPI` は環境により取得に失敗する。
