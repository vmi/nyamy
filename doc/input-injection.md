# 入力の横取りと再注入

低レベルフックで入力を握り潰し、`SendInput()` で作り直したイベントを注入する、という対で NYamy は動いている。この対が崩れたときに何が起きるか、崩れないために何を守っているかをまとめる。記載の挙動は 2026-08-16 の実測に基づく。

`mouse-event` を有効にすると、この対がマウスにも適用される。マウスはキーボードと挙動が違う箇所が多く、実際に不具合の温床になったので、以下はマウス寄りの記述が多い。

---

## 1. UIPI — 昇格ウィンドウがフォアグラウンドの間

非昇格プロセスである NYamy から見て、高整合性 (昇格) ウィンドウがフォアグラウンドにある間は次のようになる。

| | 挙動 |
|---|---|
| 低レベル**マウス**フック | **呼ばれる。** 通常アプリ宛のクリックでも `IN` の行が出る。呼ばれないのは昇格ウィンドウ自身が対象のときだけ |
| 低レベル**キーボード**フック | **呼ばれない。** 入力は昇格アプリが受け取る |
| `SendInput()` | **丸ごと破棄される。** クリックの対象が通常アプリかどうかは関係しない。判定はフォアグラウンドウィンドウのプロセスで行われる |

マウスとキーボードで違うのは、スキップの判定がキーボードはフォアグラウンドを、マウスは対象ウィンドウを見ているためと考えられる。`SendInput()` が黙って捨てられるのは AutoHotkey で知られる「管理者権限のウィンドウがアクティブだと SendInput が効かない」制限と同じもので、NYamy 固有ではない。

### なぜこれが致命的だったか

「フックは呼ばれる・注入は捨てられる」の組み合わせは、握り潰し＋再注入で成立している `mouse-event` にとって最悪の形になる。**クリックが消滅する**。

対象ウィンドウはアクティブにならないので昇格ウィンドウがフォアグラウンドに残り続け、次のクリックも同じ結果になる。昇格アプリを閉じるまで、それ以外のアプリのマウス操作が一切効かなくなる。カーソルの移動は握り潰していないので影響を受けない。

### 対処: 注入できない状態では横取りしない

`Engine::isInjectionBlocked()` (`engine.cpp`) が「フォアグラウンドプロセスの整合性レベルが自プロセスより高い」と判定した間、`mouseDetour()` は `return 0` して OS にそのまま処理させる。

- **判定はフォアグラウンドプロセス単位でキャッシュする。** トークン照会が走るのはフォアグラウンドプロセスが変わったあとの最初のボタンイベントだけで、マウス移動の経路 (毎秒数百回) では判定しない
- **トークンを開けないプロセスは「注入できない」側に倒す。** 倒す方向を誤るとイベントが消えるが、逆なら横取りをやめるだけで済む
- **横取りをやめたことはログに出ない** (フック内でログを取れないため)。昇格ウィンドウがアクティブな間にマウスの `IN` 行が出ないのが正常な状態

### 残る制約

昇格ウィンドウがアクティブな間は `mouse-event` によるマウスの割り当てが効かない。これは非昇格プロセスでは解決できず、NYamy 自体を昇格させるしかない (マニュアル `01-install.md` に記載)。同じ理由でウィンドウ調査も昇格ウィンドウには効かない ([known-limitations.md](known-limitations.md))。

## 2. 押下状態の記帳 — `m_isPressedOnWin32`

`Engine::generateKeyEvent()` は、engine が「押されていない」と思っているキーの解放を注入しない (`isAlreadyReleased`)。キーボードでは余分な BREAK が誤入力になりうるので意味のある抑止だが、**マウスボタンでは方向が逆**になる。

- 余分な UP はアプリにとってほぼ無害 (押されていないボタンの UP は普通は無視される)
- **足りない UP はドラッグのモーダルループを固める**。タイトルバーであればウィンドウがカーソルに追随したままになる

非対称なので、E1 のボタン (MakeCode 1/2/3/6/7) は `isMouseButtonKey()` で判定して**常に注入する側へ倒す**。ログには `(already released, sent anyway)` と注記が出る。ホイール (4/5/8/9) は `injectInput()` が BREAK を捨てるので対象外、`Drag`(0) も注入対象ではない。

### 記帳が飛ぶ経路

`m_isPressedOnWin32` が更新されるのは `generateKeyEvent()` を通ったときだけで、**生のまま注入する経路はどれも記帳しない**。これが desync の発生源だった。

| 経路 | 現在の扱い |
|---|---|
| ログモード中 (調査ダイアログがフォーカスを持つ間) | `injectInputThrough()` を通し、**記帳する** |
| 設定未ロード / 無効時 | 記帳しない (意図的に据え置き) |
| フォーカス未取得 | 記帳しない (意図的に据え置き) |

後ろ 2 つを据え置いているのは、これらが論理押下カウント (`m_currentKeyPressCount`) を更新しない経路だからで、記帳だけ足すと `resetModifiersIfIdle()` が本当に押されているボタンへ解放を撒きうる。マウスについては 1 つ目の対処 (常に注入する) が受ける。

### ログモードは入力キューと同期していない

`enableLogMode()` は素の bool 代入で、UI スレッドが任意のタイミングで倒せる。つまり **MAKE と BREAK の間にモードの境界が落ちうる**。実際、トレイアイコンのダブルクリックで調査ダイアログを出すと、その最初のタブストップがフォーカスを得てログモードが ON になり、注入された DOWN でウィンドウがアクティブ化すると `WM_KILLFOCUS` で OFF に戻る、という順序で「DOWN は生注入・UP は通常経路」が発生する。

この種の不具合は**再現率が 1 未満になる**。境界が DOWN と UP の間に落ちるかどうかは UI スレッドと engine スレッドの競争で決まるためで、再現しないことは仮説の反証にならない。

## 3. フック側のボタン状態

フックはボタンの押下状態を **E1 スキャンコードのビットマスク** (`m_buttonsPressed`) で持ち、ドラッグを開始したボタン (`m_dragButton`) を別に覚える。ドラッグの終了 (`endDrag()`) は、開始したボタンの解放でのみ行う。

単一の bool で持っていた頃は、左ドラッグ中に右ボタンをクリックするとフラグが落ちてドラッグ判定が壊れた。押下時に既にビットが立っていたら解放の取りこぼしとみなし、古いドラッグを終了させる。

**フック内に API 呼び出しを増やさないこと。** フックが遅くなると別の取りこぼしを生む。ビットマスクの更新とビット判定だけで完結させる。ログもフック内では取れない。

## 4. 逆方向の掃除 — `resyncKeyStates()`

ここまでは「engine は解放済みと思っているが OS では押されたまま」の話だが、逆方向 (engine は押下・OS は解放) もある。`resyncKeyStates()` が `GetAsyncKeyState()` で突き合わせて掃除する。

`scanCodeToVKey()` は E1 の 1/2/3/6/7 を `VK_LBUTTON` / `VK_RBUTTON` / `VK_MBUTTON` / `VK_XBUTTON1` / `VK_XBUTTON2` に対応させてある。`GetSystemMetrics(SM_SWAPBUTTON)` が真のときに左右が入れ替わる点は未検証のまま残っている。
